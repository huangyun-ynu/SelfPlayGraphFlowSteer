**SWE 整题真实 usage 记账与停发阈值方案（2026-09-28）**

目标是取消 SWE 请求发送前的 token 估算，使用供应商返回的真实 usage 记账；所有 Agent、修订、内容修复、重试和同池路由切换共用整题账户。正式训练配置已切换到本策略；既有 33 题和 3 题续跑配置及轨迹保持原策略语义。

1. **先定义 350,000 的含义。** 每题 Worker 累计已确认用量小于 350,000 时，允许发送下一次请求；达到或超过时，停止发送新的 Worker 请求。它是请求启动阈值，不是累计用量绝不超过的硬上限。没有请求前精确计数时，无法承诺严格不超限。

   示例：已用 340,000，发送一次请求，返回 input=14,000、output=6,000，最终累计 360,000。完整保留本次结果，记录超出阈值 10,000，此后不再发 Worker 请求。超出部分包括输入和输出，不能用单次输出上限 16,384 作为超出量的上限。

   在每题本地请求串行、usage 完整且每次物理请求均经过检查的情况下，只可能由最后一个获准请求跨过阈值。有超时未结算请求时，这个结论只适用于已确认用量，实际总量可能更高，必须明确标为未知。

2. **整题共享与作用范围。** 新策略首批应用于 SWE，阈值仍取该数据集的 350,000。账本身份由实验运行、任务、seed 和尝试 ID 确定，不能仅用 instance_id，以免不同实验共用额度。节点不是预算所有者：删除重建节点、修改 prompt、换模型、增加边、读取同伴产物、重跑、格式修复和换路由都引用同一账户。

   真正的断点恢复继续使用原账本和已确认用量。明确的新实验尝试才创建新账本，并记录 parent_attempt_id；不能把重新分配 350,000 的新实验称为预算连续的原轨迹恢复。历史三题检查点续跑应保留其当时独立新尝试的事实。

   Worker 账户统计全部实际远程模型输入与输出。Director 使用单独的模型窗口与统计字段。已存在的工具动作次数、超时和无进展规则继续各自生效；本方案不增加任何按 Agent 分割的 token 配额，也不恢复收尾额度预扣。

3. **只保留一个权威用量账本。** 新增任务级 UsageLedger；建议每个实验使用一个本地 SQLite 账本，采用事务和追加事件记录，线程间共享同一任务状态。每次物理 API 调用分别记账，逻辑请求可关联多次实际调用。产物、Runtime 和 Canvas 的累计字段从账本派生，不能再把同一份 usage 分别累加三遍。

   每条调用至少记录以下信息：

   | 字段 | 含义 |
   | --- | --- |
   | question_attempt_id | 本次实验中的整题账户 |
   | logical_request_id / attempt_id | 逻辑请求及实际调用唯一标识 |
   | agent_id / execution_id | 归属 Agent 和执行轮次，仅用于诊断 |
   | route / model / api_surface | 实际路由、模型和接口格式 |
   | request_fingerprint | 请求内容摘要，避免在账本里重复保存大段内容 |
   | usage_before_dispatch | 发出前已确认累计用量 |
   | dispatch_status | 未发送、发送意图已记录、已调用接口、状态不明 |
   | provider_response_id | 返回的响应标识；没有时保留 null |
   | input_tokens / output_tokens | 实际返回值；缺失用 null，不填 0 |
   | usage_status | 完整、部分、未知、已确认未发送 |
   | result_status | 成功、超时、服务错误、协议错误等 |
   | threshold / policy_version | 本次运行采用的阈值及预算语义 |

   每个账本对外提供 confirmed_used、usage_complete、unsettled_attempt_count、threshold_reached、confirmed_overshoot。存在未结算调用时，confirmed_used 是已确认用量的下界，不能显示为完整总用量。

4. **usage 的归一化与扣账时机。** Chat 格式读取 prompt_tokens 和 completion_tokens；Responses 格式读取 input_tokens 和 output_tokens。只有字段确实存在且为有效非负整数时才接受。total_tokens 可用于一致性核验，不要在已有输入输出之上重复相加。缓存、推理等细项必须依据接口字段包含关系处理，不能盲目加到总输入输出上。

   拿到响应后，先持久化可确认 usage，再执行内容解析、格式校验、工具调用解析和产物验收。响应格式错误仍可能消耗真实 token；不能因为后续解析异常而丢掉这次用量。响应没有 usage 也不能通过 `getattr(..., 0)` 静默当作零。

   每次实际调用只结算一次。attempt_id 是本地事件幂等键；实际路由/账户标识与 provider_response_id 作为响应重复核验信息。事件重放、重复回调、相同响应恢复不能重复扣账；真正发出的第二次重试应有新的 attempt_id，并单独结算。供应商缓存命中的请求仍按其返回 usage 计量；纯本地产物缓存复用没有新模型请求，不产生新 usage。

5. **发送流程必须覆盖每次实际 API 调用。** 在获取路由槽位之前可快速检查一次；拿到槽位后，实际发出前再通过账本事务检查。不能只在 Worker 启动时检查，因为一次执行中还可能有工具交互、内容修复、长度修复和路由重试。

   发送步骤为：读取整题账户 → 检查已确认用量和未结算策略 → 获得本题发送许可 → 持久化调用意图 → 发出实际请求 → 持久化 usage/未知状态 → 释放许可 → 交付响应。每题最多一个本地正在等待结果的 Worker 请求，避免多个 Agent 同时拿到最后一份余额；不同题目的并行请求独立运行。

   新策略不调用字节上界估算，不按估算预扣额度，也不根据剩余余额压缩输入或缩减输出。单次请求仍有路由自身的输出长度上限，用来控制单次生成长度。usage 到达阈值后，后续内容修复请求、最终总结请求及路由切换请求同样不能绕过发送检查。SDK 隐藏重试应维持关闭，重试全部由可审计的调用层管理。

6. **同池路由切换与超时未知用量。** 题目预算和路由槽位分别管理。槽位满、局部排队超时、被停用路由等没有真正发出请求的情况不扣 token，也不产生未知用量，仍可选择同池其他可用路由。预算达标是整题状态，不应触发端点故障、路由熔断或轮流尝试全部路由。

   请求已经发出后超时、连接中断、进程退出而未拿到 usage，应记录未知。不能把等待时长换算成 token，不能因为失败时间被返还就把 token 也返还，不能把 HTTP 错误码本身当作零消耗的证明。只有能够证明请求没有发出或未执行时才能记为已确认零新增。

   为保留用户要求的同池超时切换，建议缺省采用有界继续策略：第一次产生未结算调用时允许既有同池后备路由继续；同题未结算调用累计达到 2 次时，停止新的 Worker 请求并保存检查点。这个 2 是待实施的可配置失败容忍阈值，不是 token 估算或 Agent 配额。成功返回但 usage 缺失也计入未结算数；不要为了补 usage 重发一个已成功的生成请求。

   若一次超时后后备路由成功，该成功请求的 usage 正常入账，超时调用仍保留为未知。后续阈值判断使用已确认用量，同时结果报告明确显示账本不完整。上游可能在本地超时后继续执行，因此本地串行也不能保证远端没有未完成请求。

   只有供应商提供可用查询/账单/日志证据时才补账；当前提供的 GPT-student 文档没有列出这些查询能力，不能设计成必然可查。补账时以原 attempt_id 更新已知字段并追加对账事件，不能再扣一遍已确认部分。补账后达到阈值则停止新请求，已经发出的请求仍完成结算。无法补齐就一直显示未知，任务正确性与用量完整性分别报告。

7. **预算状态和结束行为。** 建议拆成两个独立维度：发送状态（可发送/请求中/阈值达标/未知用量达到容忍数/已结束）与账本状态（完整/含未结算调用），避免把有待补账直接伪装为额度用尽。

   | 情况 | 行为 |
   | --- | --- |
   | 已确认用量低于阈值，允许继续 | 正常发下一次请求 |
   | 恰好达到或超过阈值 | 停发新的 Worker 请求 |
   | 最后一次合法请求产生合格结果 | 保留结果，允许现有合法 FINISH 提交 |
   | 最后一次回复包含合法工具动作 | 按既有工具配额和幂等规则处理已返回动作，保存观察与补丁；不额外调用模型 |
   | 有补丁但缺少有效测试或合法最终结果 | 保存候选，记录达标后未提交；不伪造测试或提交回执 |
   | 未结算调用达到容忍数 | 保存检查点，终止原因记为用量无法确认 |
   | 响应需要再调用模型修复，但已达阈值 | 保留原响应和诊断，停止修复请求 |

   达标后的收尾不是一次免费的额外模型调用。Director 可以继续使用其独立预算选择当前合法 FINISH，但不能藉修改角色、添加 Agent 或切换路由启动新的 Worker 请求。预算结束应显示独立原因，例如 worker_usage_threshold_reached / worker_usage_unsettled_limit；不要再包装成 WORKER_PROTOCOL_FAILURE 或接口故障。

8. **提交与评分校验必须认识新语义。** 当前有多个环节用 `worker_tokens_used > worker_token_limit` 直接拒绝结果，仅修改发送入口会导致最后一个合法跨阈值请求的结果被拒绝。

   新回执需要携带 policy_version、threshold、confirmed_usage、usage_complete、ledger_digest 和 dispatch_policy_valid。对于新策略，检查每一次发送是否在当时已确认用量低于阈值且状态允许时获得许可，检查不存在阈值达标后启动的隐藏重试或重建节点请求。最终累计超过阈值本身不构成新策略违规。

   旧的严格上限策略继续按旧回执版本验证；缺少策略字段的旧轨迹不得被自动解释成新策略。合法的最后响应仍需满足原有补丁、测试、依赖和 Director FINISH 条件。不得为了消除预算错误绕过结果真实性校验。

   官方测评结果、轨迹是否完成和用量是否完整分别记录。用量未知不等于补丁测试失败；没有正式提交也不能伪造官方失败结果。比较总体通过率仍使用明确的全部题目分母，同时展示送评数、预算结束未提交数和用量不完整数。依赖精确成本的分析或训练准入需要单独检查账本完整性。

9. **持久化和恢复。** 发送意图先落盘，收到 usage 后先结算再交付上层。若进程崩溃发生在意图落盘与响应结算之间，恢复时把该调用视为状态待确认，不能默认为未发出而清空。若结算已落盘、产物尚未保存，恢复时不得重复扣账；重放工具动作要用原调用/动作标识检查是否已执行。

   账本恢复与整个 Director/Worker 图的恢复是不同能力。此方案保证恢复使用同一预算账本；并不声称现有只有补丁检查点的 benchmark 已经能够完整恢复所有图状态、模型历史和在途请求。启动清单应明确是恢复原尝试还是创建新的实验尝试。

10. **同时修复检查点测试证据关联。** 上次三题续跑在工作区创建时预先应用补丁，没有把这一操作登记为进度校验认可的起点。应由 runtime 生成可信的 workspace_restored 事件，包含补丁 SHA、任务/base_commit 绑定和恢复后的 workspace_version。

    `_finalize_swe_progress` 以这个可信初始版本建立修改起点；在该版本执行的真实测试可计为恢复后的测试。后续编辑增加版本并使旧测试失效。由模型在文本里声称恢复或测试，不构成证据。这样 Pylint 和 SymPy 的已执行测试可以得到正确识别，无须为了取得测试资格额外改一次文件。此修复不会自动解决图未连通、旧结果失效等其他提交阻塞。

11. **配置与代码落点。** 正式训练配置使用以下字段：

```toml
[canvas.worker_token_budget_by_dataset.swe_bench]
policy = "reported_usage_threshold_v1"
start_threshold = 350000
accounting_scope = "question_attempt"
max_inflight_requests = 1
unknown_usage_policy = "continue_bounded"
max_unsettled_attempts = 2
```

    配置解析时禁止同时为同一任务启用相互冲突的新阈值模式和旧固定额度/预留模式。运行清单、轨迹、回执和汇总都带策略版本；阈值模式与严格上限模式的旧成绩不能混为同一种预算实验。

    | 文件/模块 | 待实施修改 |
    | --- | --- |
    | 新 worker_usage_ledger.py | 任务账本、发送许可、幂等结算、未知用量和恢复 |
    | config.py / application.py | 解析数据集级策略，创建并传递同一账本 |
    | llm.py | 在每次实际发送入口检查；优先记录 usage；移除新模式的估算准入 |
    | endpoint_pool.py / backend_failures.py | 预算终止不触发 failover；普通路由失败继续按池规则处理；传递同一账本 |
    | runtime.py | 工具循环、解析修复、最终输出请求共用账本；产物统计不重复扣账 |
    | canvas.py / unified_submission.py | 调度合法动作读取账本；达标时收尾；保留有效候选 |
    | submission_contract.py | 带策略版本的回执，验证发送许可而非一律拒绝跨阈值累计量 |
    | outcome_admission.py / swe_failure_attribution.py | 区分达标、用量未知、协议失败和官方测评失败 |
    | swebench.py / runtime.py | 恢复事件及恢复后测试版本关联 |
    | benchmark 汇总与运行清单 | 实际用量、未知数、阈值超出量、预算结束原因和策略版本 |

    运行日志应显示：已确认用量 / 阈值、是否仍可发请求、是否有未知调用、跨阈值的最后调用。除独立的 Director 当前窗口 token 统计外，新 Worker 准入路径不使用预估输入 token、字节长度折算或平均历史请求成本。

12. **验收标准。** 重点验证真实调度与记账语义，不仅测试几个辅助函数。

    | 测试场景 | 必须观察到的行为 |
    | --- | --- |
    | A 用 180k，B 再用 100k | 整题已用 280k，后续使用同一账户 |
    | 字节估算很大，但确认量未达标 | 新策略不调用估算器，正常发送 |
    | 340k 时请求返回 20k usage | 结算到 360k；结果保留，下一请求被拒绝 |
    | 发出前已用恰好 350k | 真实 API 调用次数不增加 |
    | 内容修复/长度修复时刚好达标 | 后续修复没有发出 |
    | 槽位排队失败 | 零新增 usage、无未知条目，切换同池可用路由 |
    | GPT 超时，student 成功 | GPT 为未知，student 真实 usage 入同一账本 |
    | 未结算调用达到 2 | 停止新请求、保存检查点；其他题目继续补位 |
    | 回复可用但缺少 usage | 不填零，不为补 usage 重发同一请求 |
    | 使用量已返回但内容格式错误 | usage 仍被结算 |
    | 同一事件重复消费/恢复 | 只结算一次 |
    | 删节点、改职责、换路由、恢复 | 不清空整题账本 |
    | 同题并发争抢最后发送资格 | 只允许一个本地请求在途，后者结算后重新判断 |
    | 阈值后产生正确完整结果 | 新策略回执有效，允许合法 FINISH |
    | 阈值后偷偷发额外调用 | 回执审计发现违规，不误判为正常跨阈值 |
    | 有补丁而缺测试 | 保存未提交候选，不伪造成功 |
    | 恢复补丁后直接运行测试 | 对应 workspace_version 的测试被进度校验认可 |
    | 测试后又编辑 | 旧测试不再证明新版本已测试 |
    | 旧策略回归 | 原严格上限语义仍按旧模式验证 |

13. **实施与验证顺序。** 先落账本和请求入口、usage 归一化，再接入路由池、Worker 工具循环与所有修复路径；随后同步修改 Canvas、回执与结果归因，避免只放宽入口而尾部继续拒绝。检查点测试证据修复单独验证，报告中分别标记两个修复。

    第一轮使用既有 7 题的已记录真实 usage 和模拟故障做离线回放。旧日志中被拦截的请求并没有实际返回 usage，不能臆测其本来会消耗多少，更不能据此宣称题目会通过；离线只能验证相同已知状态下新策略是否仍误拦、是否重复扣账。

    第二轮进行少量真实请求验证，覆盖普通完成、跨阈值收尾和当前接口 usage 形状；故障与极限边界主要用可控回归验证，避免为制造超时或 token 消耗而反复调用外部服务。最后再运行需重试的具体失败题，保存新的实验目录及预算策略标记，再决定是否进行整批 33 题对照。

    并发验收沿用用户指定的 15 条轨迹滚动补位、GPT-student 10 / GPT 非 eco 5、远程测评并发 4。每题本地模型调用串行不影响跨题滚动并发。使用已保留的 Director；远程测评服务器用完按 STOP_CHARGING 关闭。

14. **本方案的效果边界。** 它消除 Worker 的估算误拦，准确保存已知用量，并阻止达标后的隐藏重试和预算失败循环。它不保证使用更少的真实 token、不保证低于 350,000、不保证远端超时请求的 usage 可以查回，也不直接解决 Director 32k 历史膨胀。后一问题仍需单独处理在线快照重复与收尾轮次成本，并对新的预算策略单独统计结果。
