# 提前绑定输出与有界恢复方案（待实施）

> 已被 [增量执行、结果职责与最终提交解耦方案](INCREMENTAL_RESULT_AND_SUBMISSION_DESIGN.zh-CN.md) 替代。以下保留作为历史设计，不再推荐“首个 Worker 前固定输出身份”或特殊输出替换流程；统一评估、候选版本保护、有界恢复等原则在新方案中继续保留。

日期：2026-09-26。针对实验目录 `SelfPlayGraphFlowSteer-output-contract-v1`。本文件是设计方案，未修改执行逻辑，也未启动新的付费推理。正式目录和已有 286 题评测产物保持原样。

## 1. 结论与适用范围

建议第一版采用：**首个 Worker 执行前绑定输出 Agent；首次执行后，本题输出身份固定；新证据通过真实图依赖进入同一个输出 Agent；提交检查与修复执行分开。**

作用范围限定为已有文本提交协议的 AIME、NQ、HotpotQA、HealthBench。ALFWorld、WebShop、SWE 保持各自环境/代码提交规则，不套用文本输出身份锁。

这比上一轮讨论中的“仅要求最终输出 Agent 在自身第一次执行前绑定”更严格。后者允许普通 Worker 先执行，但如果之后禁止把它升级为输出，就可能被迫额外创建 Agent，增加调用、占用节点预算，甚至在节点满额时无路可走。

第一版不增加“等整个图规划完成再执行”的新调度阶段，也不增加普通执行调度动作。输出可以先产生初版答案；新增真实上游证据后再修订。它不是专门的 formatter，也不要求固定星形结构或固定 Agent 数量。

## 2. 已确认的代码约束与失败证据

- 当前 `SET_MODEL` 会执行已配置且失效的 Worker；未完成当前 Agent 配置前，通常不能继续添加其他节点。
- 已有早绑定测试证明 `SET_PROMPT → SET_OUTPUT → SET_MODEL` 可以在零 Worker 调用时绑定，并让第一次 Worker 调用使用输出职责；现在只是允许，没有强制。
- 当前文本输出角色参与输入签名，晚绑定会触发 `output_contract_changed`。AIME 22 的第 3 轮答案是 754，第 10 轮晚绑定重跑成为 125，第 11 轮恢复成为 109。
- AIME 15 和 22 均出现 `output_health=usable`、`repair_reason=null`，但 finish 因 `terminal_tool_failure` 被拒绝。
- 两题连续拒绝后冻结编辑，只剩 finish；一次自动恢复已经耗尽，后续 finish 不再执行 Worker，最终无进展终止。
- 文本 Worker 工具预算当前按 `execution-{sequence}:{agent}` 划分。不能在增加重试时，因创建新 execution 序号而无意重置工具额度。

## 3. 输出绑定规则

### 3.1 第一版规则

1. 文本任务开始时 `output_binding=unbound`。
2. 在任何可能触发首个 Worker 的入口之前，必须已经完成显式输出绑定。
3. 默认流程：ADD_AGENT → SET_PROMPT → SET_OUTPUT → SET_MODEL → Worker 首次执行。
4. 绑定本身不执行 Worker、不发模型请求、不读取标准答案，不创建提交凭据。
5. 首个 Worker 执行开始时锁定输出身份。此后不得切换输出、删除输出 Agent，或通过恢复/直接 Runtime 入口悄悄改变身份。
6. 输出 Agent 的 prompt、模型路线和有效上游依赖仍可在既有规则下修改。身份固定不代表内容固定。
7. 首次执行前，允许合法配置修正；如果允许撤销绑定，必须在没有 Worker 已执行且没有请求在途时原子完成，保留绑定历史。不得出现运行后解除锁再重新绑定。
8. 正式提交后，绑定、图快照、答案和凭据保持不可变。

### 3.2 必须明确的代价

当前配置流程是逐 Agent 完成，因此此规则意味着：首个配置的普通 Agent 承担最终交付职责，Director 必须据此委派它。单 Agent 题无需额外节点；多 Agent 题通过真实依赖向它提供证据。

第一版放弃“看过所有候选后直接把另一个已执行 Agent 选作最终输出”的能力。这是行为变化，必须在新提示词、新执行语义版本和对照实验中明确记录。若未来要求任意选择多个尚未执行的草稿节点，则需要另行设计可暂停配置的图构建阶段，不在本次混入。

### 3.3 防绕过

检查不能只写在 Director 提示词。Canvas、Runtime 执行入口、无显式 SET_MODEL 的自动执行入口、恢复入口和回放入口均要遵守同一绑定状态。

重复绑定当前节点不得触发 Worker，也不得算作有效进展。绑定另一节点必须在修改图之前拒绝。旧轨迹和旧缓存不得被默认解释成已遵守新规则。

## 4. 执行时机与图结构

“输出身份确定”与“当前执行条件满足”分开处理：

- 已声明依赖尚未完成时，使用现有调度/组件规则处理，不提交依赖不完整的答案。
- 没有上游依赖的单 Agent 可以立即执行，产生完整任务的初版候选。
- 新增 Helper 后，通过实际关系将其贡献接入输出；合法关系候选和 off 决策都不是边。
- 上游有效产物变化时，按真实依赖失效并修订输出，这是必要重算。
- 所有节点都指向输出并不要求直接连接；保留多层结构和受现有约束的双向组件。
- 输出锁定后，output_reachability 修复菜单应提供层级修改、关系考虑、删除无贡献的非输出节点等合法动作，不再提供切换输出作为修复手段。
- 不能因需要连接图就把 off 自动改成 on；关系仍由现有策略决定。

不预测未来是否还会添加 Agent，不等待“整个任务已经思考完毕”。因此，本方案消除的是角色晚切换造成的执行，不能承诺每个输出只执行一次。

## 5. 统一输出评估

新增无副作用的共享输出评估对象，供控制快照、可执行动作、提交检查、恢复和日志共同读取。

建议字段：

```text
bound_output_agent
binding_locked
artifact_id / artifact_input_signature
artifact_status
blockers[]
submit_ready
repair_allowed / repair_block_reason
repair_attempts_used / remaining
```

它区分两层：产物本身是否完整，以及当前图/配置/预算条件下是否可以提交。不能把所有条件压成一个“答案非空”。

| 状态 | 含义 | 允许的处理 |
|---|---|---|
| UNBOUND | 未指定输出 | 绑定，禁止 Worker 执行 |
| CONFIGURING | 输出配置未完成 | 补齐配置 |
| WAITING_INPUTS / STALE | 已声明依赖未完成或产物输入过期 | 完成依赖、执行当前版本 |
| NEEDS_REPAIR | 已有产物，但有可定位的完整性问题 | 有界修复或真实图/委派修改 |
| READY | 当前产物和提交前置条件均满足 | 显式 finish；仍允许有依据的图修订 |
| FAILED | 没有合法恢复且不能提交 | 记录具体终止原因 |
| SUBMITTED | 已接受 finish 并签发凭据 | 结束 |

状态之外保留全部 blockers，避免只显示一个原因掩盖其他阻塞。

答案正确性、格式、范围、模型低置信度和一般数学不确定性不成为新的提交门槛。非空错误答案仍按当前评分协议提交并评分；无答案、协议失败、严重执行完整性风险、旧输入绑定等仍需阻止提交。

## 6. 将 finish 与修复调用分开

建议新增一个显式、受限的 Director 动作：

```json
{"action":"repair_output"}
```

目标自动限定为已绑定输出 Agent。Runtime 将其绑定到当前产物版本和具体问题，不接受模型自报“修好了”作为证据。

### 6.1 finish

- 对已满足提交条件的产物，只做最终复核、确定性答案提取和签发凭据；零新增 Worker 调用。
- 不在 finish 内隐式重算或再次求解，移出 `_prepare_text_submission` 当前的一次自动恢复行为。
- 遇到过期、缺失或有完整性风险的产物，提供明确阻塞与合法下一步；不得伪造成功提交。
- 提交前复核输入签名、依赖版本和当前图，避免检查和签发之间产物变更。
- Worker 修复成功也不自动提交；仍等待真实 Director finish 动作。

### 6.2 repair_output

- 仅在评估器确认有可恢复问题且预算允许时开放。
- Worker 可见恢复原因、相关真实工具报错、当前限制、剩余工具额度、可用证据和原有候选，不接触金标。
- 同步复用现有 Worker/工具执行链并记录完整请求响应，不让 Director 写具体解题步骤。
- 建议初始上限为每题 2 次显式输出修复，作为待验证配置；并不是保证一定执行两次。没有对应工具/时间/token/轮次预算时，不开放无效修复。
- 恢复计数不因换 prompt、换层级、拒绝动作、API 重试或新 artifact ID 清零。
- 修复继承被修复执行的工具预算作用域，不能借新 execution 序号获得新的 initial 工具额度。若未来要追加恢复工具额度，必须成为独立显式配置、计入总账并单独对照，本方案不暗中增加。
- 原执行中真实新增任务输入引起的正常计算与失败重试分开记录，避免将所有图修订错误地当作恢复。
- 执行修复前为之后的一次显式 finish 留出 Director 轮次；没有可交付产物且无法保留收尾空间时记录预算终止。

工具额度为 0 不等于所有恢复都不合法：如果问题仅是响应封装，且现有证据足以重新输出，可以在剩余模型预算内恢复；如果恢复必须获得新的工具执行结果，则不能宣称仍有这条恢复路径。修复类型和所需资源必须一并进入评估结果。

### 6.3 冻结规则

冻结应限制反复无效的拓扑修改，不应覆盖合法输出修复。按状态产生动作菜单：

- READY 时可以 finish。
- NEEDS_REPAIR 且预算允许时可以 repair_output，即使拓扑编辑冻结。
- 图结构本身未满足要求时，仍开放能解决该问题的有限图操作。
- 没有可提交产物、也没有可执行修复时，直接终止并记录原因。

不允许再出现 `allowed_actions=[finish]` 且已知 finish 永远不能通过的稳定状态。预算消耗、换错误文案和重试次数增加不能被当作语义进展。

### 6.4 修复进度与循环检测

保留普通状态循环检测，并让专门的修复进度检测覆盖 `output_reachability` 和所有输出提交阻塞。两类检测不能只依靠输出节点 ID、artifact ID 或执行次数判断进展。

- 连通性修复依据已激活的真实边、无法到达固定输出的节点/组件，以及阻止合法连接的层级约束。候选边、off 决策和输出标签变化不算连通性改善。
- 输出修复依据当前输入版本是否得到完整有效产物、相关严重风险是否消除、提交阻塞是否实质减少。单纯增加一个失败尝试、换一条报错、消耗预算不算恢复成功。
- 必要的多步修复可以继续，但使用有限修复轮次并保留未解决问题的累计记录；不能每改一次 prompt 或新增节点就把停滞计数清零。
- 真实新增证据可以触发正常计算；同一未解决问题反复出现时，仍受本题修复上限、总轮次和总预算约束。

阈值优先复用当前配置，通过模拟多步合法修复和循环序列确认不会误截断；若需调整，作为显式配置进入对照实验，不为了两条轨迹单独放宽。

## 7. 候选保留与输入绑定

保留每次执行的不可变候选，并分别记录“最新尝试”和“当前输入版本的可提交候选”。

新尝试发生协议失败或严重工具失败时，不直接抹掉同输入版本下仍然有效的候选指针。覆盖依据仅为协议、完整性和版本，不是答案正确性、模型置信度或标准答案。

严格限制：

1. prompt、输出合约、模型配置或有效上游证据改变后，旧候选只能作为历史证据，不能直接作为新输入的正式提交。
2. 恢复提示的实际请求哈希和任务语义输入绑定都要记录。复用必须证明属于同一授权的当前输入版本，不能仅按 agent_id、题号或答案文本相同判定。
3. 候选完整性引用生成该候选的执行证据与相关依赖；全历史失败次数另作遥测，不能把无关失败混进该候选的身份和证据。
4. 第一版不提供跨输入版本自动回退；输入过期后宁可明确修复失败，也不提交历史正确答案。
5. 不允许隐藏评测结果指导候选选择，不从其他 Agent 的答案池自动挑选。

因此，AIME 22 的历史 754 只能作为真实故障证据。新协议重跑第一次收到的提示词不同，不能预先承诺仍会产生 754。

## 8. 错误归因与终止记录

保留原有 outcome 状态体系，在终止账本中补充结构化来源和具体原因：

- 可证实的模型代码/动作/协议失败：在满足既有归因规则时记 policy_failure。
- 后端、沙箱基础设施或控制器异常：保留未知结果/不可训练属性，并明确原因。
- 只有字符串 `Traceback (most recent call last)` 不足以归因为模型错误；需从工具执行层记录异常类别及来源。
- 工具超时需要结合受控执行证据归因，不能把所有超时统一判为答错。

未产生真实提交凭据的任务保持未提交。全题成功率按完整计划数统计；保留原始 null 分数及未评分原因，不通过改统计口径制造提升。

## 9. 边界情况与预期

| 情况 | 预期 |
|---|---|
| 单 Agent 原子任务 | 提前绑定同一个普通 Worker，无额外 formatter/输出 Agent |
| 首个 SET_MODEL 发生在绑定前 | 执行前拒绝，Worker 调用数仍为 0 |
| 无显式模型选择的自动执行路径 | 同样被绑定检查拦截，不存在旁路 |
| 首次执行后切换/删除输出 | 修改图之前拒绝，不重跑、不清计数 |
| 重复绑定当前输出 | 不执行 Worker，不算进展 |
| 新增真实上游证据 | 输入失效并正常修订；旧候选不能直接提交 |
| consider_relation 返回 off | 不创建边、不宣布图已连通 |
| 双向组件/多层图 | 沿用组件执行与依赖规则，不强制星形图 |
| 输出为空/Worker 协议错误 | 标为需要修复或终止，不显示 READY |
| 非空但格式错误/答案错误 | 执行完整性通过时可提交，由 verifier 评分 |
| 早期工具报错、后续成功恢复 | 依据当前相关执行证据清除已恢复风险 |
| 末次工具失败、修复还有预算 | 开放显式有界修复，不藏在 finish 里 |
| token 有剩余但工具额度已耗尽 | 不谎报仍可执行工具恢复，不通过新作用域刷新额度 |
| 冻结后产物仍有风险 | 合法修复或明确终止，不无限 finish |
| 新失败尝试与旧有效候选输入完全相同 | 保留旧候选及绑定，不按金标选择 |
| 输入已变化但历史候选正确 | 历史留存，禁止越过绑定提交 |
| finish 重复调用/保存恢复后再次 finish | 已签发凭据不可变，不重复提交或评分 |
| 旧轨迹/缓存/训练样本 | 保留旧版本语义，禁止混用 |
| 状态化环境任务 | 保持原有环境提交、会话与预算约束 |

## 10. 代码落点与版本

| 模块 | 拟改动 |
|---|---|
| `config.py`、`actions.py`、`director.py` | 显式早绑定策略、修复额度、新 repair_output 动作及提示词 |
| 新共享输出评估模块、`canvas.py` | 状态评估、绑定锁、候选状态、冻结动作菜单及 finish 检查 |
| `runtime.py` | 所有执行入口的绑定断言、候选提交指针、版本校验、修复预算作用域 |
| `adaptive.py` | 去掉 finish 内隐藏恢复，接入显式恢复与统一终止账本 |
| `submission_contract.py`、`outcome_admission.py` | 延续真实 finish 凭据，完善版本与失败来源 |
| `execution_contract.py`、回放/训练消费方 | 新旧语义隔离，缓存、PATS、训练样本和反事实回放兼容性检查 |

建议以新的实验开关和语义版本实现，Director 动作协议/提示词版本、输出绑定策略版本及相关缓存/训练 lineage 一起更新。具体版本号在实施时统一分配；不得把新行为悄悄写入旧版本。正式目录不直接切换。

## 11. 实施与验证顺序

1. **先固定现状与断言。** 保留 286 题运行和两条失败轨迹；添加能复现状态矛盾及冻结死路的回归用例。
2. **先统一评估、明确恢复。** 在兼容策略下修复共享状态与显式恢复机制；核验所有计数及提交凭据。无需依赖提前绑定也应能避免恢复死路。
3. **接入提前绑定及身份锁。** 新策略单独启用；按首次执行、角色变化、依赖更新及不同 Runtime 入口验证。
4. **接入候选版本保护。** 明确同版本候选保护和跨版本禁止回退，验证缓存命中、失败尝试和异步/恢复后的版本冲突。
5. **模拟与性质测试。** 覆盖上述矩阵，并生成 1–4 节点的合法/非法操作序列；验证不会未绑定执行、越预算恢复、把候选边当已有边、提交过期产物、重复签发凭据或无限无进展。
6. **真实轨迹测试。** 原始日志先在旧协议回放确认故障；新协议下重放失败观察与状态条件，明确标为反事实模拟。不能将旧模型响应冒充新提示词真实输出。
