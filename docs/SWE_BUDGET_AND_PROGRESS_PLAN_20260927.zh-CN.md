# SWE 共享额度、重复请求与任务进展改造方案

状态：设计方案，尚未修改运行逻辑或启动对照实验。

前提：Director 成功编辑总上限 24、SWE 工具总上限 32。所有节点、initial/revision、删除重建共用一个整题账本。finish 提交已有合格结果。本方案不额外改变上下文与训练语义。当前按用户最新要求[恢复包含 thinking 的增量式上下文](DIRECTOR_INCREMENTAL_CONTEXT_20260927.zh-CN.md)，保留真实 token 前缀、mask 和合并训练检查，概率审计只存离线。

## 1. 全局收尾预留

### 当前依据

`runtime.py::_swe_action_stage_rejection` 在 `commit_required=False` 时直接返回。当前 `_SWE_FINAL_FIX_ACTION_RESERVE=2` 因而只保护最终职责的局部执行。`MultiAgentRuntime.swe_execution_blocker` 只在共享余额为零时拒绝新执行。

### 建议规则

新增仅对 SWE 生效的整题收尾策略，预留初值为 4。这是 32 内部的限制，不是额外的工具账户；4 是待对照验证的初值，不是已经证明最优的数值。

未形成当前可提交候选时，对普通探索节点显示：

`exploration_available = max(0, remaining - 4)`

例如已用 28 次、剩余 4 次，普通 subtask 停止发起新的探索调用，将已取得的证据与补丁交回 Director。收尾节点继续使用同一个账本的 4 次余额。4 次可支持一次定点读取、一次 edit/apply、一次测试及一次有限调整；它不保证任意复杂任务都能在 4 次内修复。

不能只将原有 role 条件删掉：新工作区往往需要先读源码获取 SHA，或者先应用上游 CodeArtifactRef；上游测试也不能直接当成新工作区的测试。

收尾执行按当前工作区状态准入：

| 当前状态 | 准入规则 |
| --- | --- |
| 尚无补丁，余额 3 或 4 | 可进行必要的定点读取；读完必须仍可执行 edit + test |
| 尚无补丁，余额 2 | 有充分现有证据时可 edit/apply，随后留下 1 次 test；禁止再探索 |
| 有未测试修改，余额 1 | 只允许当前版本的测试 |
| 最新补丁已经测试 | 可以提交；若再 edit/apply，必须至少还有修改和重测的 2 次额度 |
| 当前已有有效可提交候选 | 不再为“从头产出补丁”占用预留，优先展示 finish；使候选失效的变更须重新检查可完成性 |

补丁恢复、测试失败重试都正常扣额。启动后失败的调用不退款，重建节点也不生成新预留。

### 调度和依赖必须同步处理

收尾保护覆盖执行器中的每个调用，以及新节点、dirty 重跑、显式 run_agent、自动执行和双向修订的启动准入。

调度前展开 task_result 的必需依赖和待完成的修订波。预留不能使必要上游无法完成，形成“留了额度却不能收尾”的死锁。普通探索不能侵占已经识别出的必要依赖调用和最终 edit/test 调用；必须完成的依赖属于收尾路径，而不能仅凭 subtask 标签拒绝。

若某次图编辑会新增不可负担的必需执行或修订，应在提交该编辑前返回明确的预算不可完成反馈。若当前图已无可完成路径，保留 dirty/stale 的真实状态，允许 Director 做合法图修复或结束；不自动删除依赖、改变节点职责或把第一轮产物当成已完成修订。

预留到达是交接条件，不等于整题工具耗尽或模型失败。返回 `swe_closure_reserve_reached` 以及 remaining、exploration_available、收尾状态；当前 Worker 可以有界文本收尾并导出已有补丁，不再为拒绝的新调用创建假产物。

## 2. 重复只读请求在扣额前拒绝

### 当前依据

`ModelAgentExecutor.execute` 先调用 `ActionBudgetLedger.consume`，再用 `_swe_read_only_signature` 判断重复。因此被拒绝、未执行的同一读取已经扣额。

完全相同请求的去重目前在修改前后都生效；只有“只读语义停滞”的阶段约束还主要作用于未修改阶段，这两者要区分。

### 新调用顺序

1. 校验工具名、参数、当前工作区版本与阶段准入。
2. 检查该执行中是否已成功完成相同只读请求。
3. 重复则返回 `repeated_no_progress_action`，标记 `executed=false, charged=false`。
4. 通过检查后再进行账本准入、扣额，然后执行工具。
5. 根据可信结果更新证据、修改、测试和停滞状态。

只对能在实际执行前确认的重复请求免费拒绝。已经派发的超时、异常、测试失败，以及“执行后才发现结果没有新内容”的调用仍扣额，避免免费重试。账本的检查和扣额应在同一准入边界内完成，批量请求逐项处理。

去重键包含执行/工作区身份、版本、工具名和规范化参数。规范化只处理确定等价的默认值、参数顺序和路径表示，不把不同搜索表达式随意视作等价。

只有外层调用成功且内层 `output.status=ok` 的有效观察进入成功缓存。内部错误不能缓存成成功，也不能阻止恢复后的合理重试。工作区变化后允许再次读取。

第一版不做跨独立工作区的硬性免费去重。新节点可能确实需要重新读取以获得本工作区的 SHA；跨节点是否产生新信息由第三项的整题证据账本判断，而不复用旧工作区的版本字段。

### 免费拒绝的停滞保护

保留默认阈值 4，但统一统计当前 Worker 的无有效进展请求：重复拒绝、无效请求、换参数但只取得已有证据等，不能靠混用错误码互相清零。

第 3 次给出最后一次恢复提示，第 4 次结束该 Worker 的工具循环，进入既有有界文本收尾。只有真实的新局部证据、修改或测试证据才能清零，不按“收到了一条 status=ok”清零。修改之后也适用。

免费拒绝仍消耗实际模型 token，并进入原始轨迹。工具额度保持 32，已有 token/deadline 保护保留。基础设施故障即使触发停止，也不因此被改判为模型策略失败。

## 3. 按整题工程证据判断进展

### 当前依据

`unified_submission.py::_unified_progress_signature` 包含图、节点、pending/dirty、answer/summary、artifact 和 resource 信息。改 prompt、改节点 ID 或重写汇报可以产生新签名。

Canvas 的 `_record_unified_progress` 和 Director 主循环又分别保存已见签名及停滞计数，需要统一同一层级的状态来源。

### 任务证据账本

新增按 episode 隔离的 `SWEProgressLedger`，生命周期与共享工具账本一致，只有新题/新 episode 才重置。删除节点、换模型、改 prompt、重建工作区不清空已见工程证据。

| 可信变化 | 是否形成整题新进展 |
| --- | --- |
| 读到之前未覆盖的代码区域或内容 | 是；按路径、内容版本与覆盖区间去重，重叠部分不重复计数 |
| 搜索/目录观察提供了新的代码位置或定位证据 | 是；相同命中不重复，单纯换关键词并继续得到空结果不重置主计数 |
| 产生之前未见的有效非空补丁 | 是；使用绑定 base_commit 的补丁内容指纹 |
| 在指定补丁上实际执行了新的测试，或测试结果发生实质变化 | 是；绑定 patch、profile、target、实际执行标记和稳定结果 |
| 配置/关系修复让既有候选可以合法提交 | 有界记录一次，给出 finish 机会 |
| 改 prompt、模型、节点 ID、自然语言 answer/summary | 本身不构成工程进展 |
| 新 artifact ID、workspace_version、action_index、剩余额度变化 | 本身不构成工程进展 |
| 相同补丁和测试反复出现，或补丁 A→B→A | 已见状态不重置停滞 |
| 测试被拒绝、环境准备失败、未执行测试、仅打印成功文案 | 不构成测试进展 |

补丁内容变新不等于修复正确；不通过粗暴删除空格/注释来“归一化语义”，避免破坏 Python 缩进、字符串等有效差异。预算上限和正式验证继续约束质量。

测试结果指纹忽略临时路径、耗时、时间戳和 action_index，保留真实退出状态、实际测试信息及稳定的失败标识。完整输出留在原始日志。代码编辑之后，旧测试证据仍留档，但不能满足新补丁的测试要求。

### 避免误杀合理的建图和修复

建节点通常需要 add_agent → set_prompt → set_model，关系选择也有固定协议步骤。把这些定义为有界配置事务：事务内部给予完成所需的有限宽限，事务完成或放弃时统一判定是否产生工程进展；每次实际图修改仍正常计入 24 次编辑。

默认连续 4 个完整的调度/执行机会没有新增工程证据时停止。新 ID 或改 prompt 不能启动无上限的新宽限。事务中途取消也消耗一次无进展机会，重复协议错误保留现有有界保护。

已有候选因为合法图修复恢复可提交时，保留一次 finish 机会。恢复名额以补丁/测试证据身份记账，不用节点 ID 或整个图的散列，反复加删无关节点不能刷新名额。

整题停滞计数由 Canvas/任务进展控制器唯一维护，Director 读取它，不再独立维护第二套同级计数。Worker 的局部动作停滞与整题停滞仍有不同时间尺度，但使用同一套可信证据定义。

原有图版本、输入绑定、dirty/stale 和缓存签名继续服务于产物有效性校验；只替换 SWE 的进展判断，不能为了减少误判而放松陈旧产物提交检查。其他数据集沿用既有规则。

## 4. 代码落点和实施顺序

| 位置 | 改动 |
| --- | --- |
| `runtime.py::ModelAgentExecutor.execute` | 去重前置、明确 charged/executed、Worker 无进展计数、收尾调用准入 |
| `runtime.py::MultiAgentRuntime` | 任务证据账本生命周期、全路径执行准入、必要依赖/修订计划检查 |
| `runtime.py::_swe_action_stage_rejection` | 从最终职责的局部规则扩为共享收尾规则，保留按当前工作区的 edit/test 顺序约束 |
| `swebench.py` 与公共测试 runner | 从真实结果产生可信修改/测试证据；需要时补充稳定测试结果标识 |
| `unified_submission.py` / `canvas.py` | SWE 语义进展、唯一整题计数、事务宽限、候选恢复机会 |
| `director.py` | 使用统一进展计数与恢复反馈 |
| `application.py` / 配置 / manifest | 记录策略版本、预留值和停滞阈值，支持独立开关与对照 |

落地次序：先建立统一证据与停滞控制，再把重复拒绝移到扣额前，最后接入全局收尾预留和调度检查。这样免费拒绝从启用起就具备完整的循环保护。

建议初值（字段名为拟新增，当前尚不可直接用于配置）：

```toml
swe_closure_reserve = 4
swe_duplicate_read_policy = "reject_before_charge_v1"
swe_progress_policy = "task_evidence_v1"
swe_worker_no_progress_limit = 4
swe_director_no_progress_limit = 4
```

## 5. 验收和对照

必测用例：

1. subtask 连续探索到剩余 4 次时正常交接，task_result 可以完成 read/edit/test；全题消耗不超过 32。
2. 已有补丁需要 apply + test，不能误把上游测试当成新工作区测试；已测试补丁最后一次额度不能再次修改。
3. 新建、重建、dirty、run_agent、双向修订、不同 runtime route 都不能绕过预留；必要依赖不会被简单按角色挡死。
4. 同版本成功重复读取不扣额；版本/内容变化后允许读取；失败观察不会毒化成功缓存。
5. 重复、无效参数、status 和无新信息读取交替出现，仍在有界次数内收尾。
6. 改 prompt、换节点、改 summary 不重置整题进展；新代码区域、有效补丁、实际测试能更新证据。
7. 正常建图能完成；A/B 补丁切换不刷进展；合法图修复能提交原候选，循环图编辑不能无限续命。
8. 已知模型失误、预算交接和基础设施故障分别归因；不把“预留已到”直接记成整题失败。
9. Director 和 Canvas 的整题计数一致；新增反馈只追加，不改历史消息、训练 token 前缀和 mask。

对照以当前已补公开功能测试的版本为基线。固定任务集合、种子、模型路由、24/32 额度，比较基线、仅预留、仅免费去重+必要循环保护、仅语义进展、完整方案。预留值另比较 2 与 4；先用小批检查行为，再用一致的 128 题集合做配对比较。

主要指标：任务成功率、非空补丁率、最新补丁实际测试率、因前序节点耗尽额度而无法收尾的比例、重复拒绝扣额数、无证据建图循环次数、误停滞比例、工具/token/耗时和基础设施故障占比。节省调用不是单独的上线依据，应报告每题变化与样本不确定性。

新策略使用新的运行目录和策略版本记录，原始冻结结果保持原样。进展账本的明细留在离线审计中；Director 只收到短的当前状态和拒绝原因，训练历史继续增量追加。
