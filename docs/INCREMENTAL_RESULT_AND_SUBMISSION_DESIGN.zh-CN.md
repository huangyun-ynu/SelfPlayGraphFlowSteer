# 增量执行、结果职责与最终提交解耦方案（待评审、未实施）

> 已被 [全任务统一增量执行与提交协议](UNIFIED_INCREMENTAL_EXECUTION_AND_SUBMISSION_DESIGN.zh-CN.md) 替代。本文保留为文本任务范围的历史设计；新版将 ALFWorld、WebShop、SWE 一并纳入，所有新版任务均取消 set_output，并统一完整任务结果、显式继续执行、资源生命周期和提交事务。

日期：2026-09-26。适用实验目录 `SelfPlayGraphFlowSteer-output-contract-v1`。

本方案替代此前“首个 Worker 前固定输出身份”和后续“受控替换输出”的建议。此前方案仍把解题职责与最终提交节点绑定，限制增量修改后又需要特殊交接流程，复杂度与限制均不必要。本文没有修改运行代码、原评测成绩或已冻结的运行产物，也未启动新推理。

## 1. 推荐决策

**配置时明确每个 Agent 交付什么；执行时只依据职责和真实依赖；提交时由 Director 指定一个已存在、当前有效、符合提交前置条件的完整任务产物。**

- 不强制第一个 Agent 承担最终回答职责。
- 不永久绑定任何 Agent ID，不增加 `replace_output` 动作。
- 正式提交前，可以按普通增量操作修改、删除、创建任何节点。
- 新文本协议移除独立 `set_output` 动作，改为 `finish(target)`。
- 为局部任务或完整任务生成结果，是执行前确定的配置；最终选谁提交不进入 Worker 输入。
- `finish` 不生成、重写、拼接答案，也不调用 Worker 或隐藏 formatter。
- ALFWorld、WebShop、SWE 保留环境提交规则；本次限定 AIME、NQ、HotpotQA、HealthBench 文本任务。

“提前明确”的对象是交付职责，不是本题最终 Agent 身份。多个节点可以承担完整回答职责；也允许探索阶段暂时全部是局部节点。正式结束时必须存在可提交候选。

## 2. 已核实的根因与约束

当前 `output_contract.py` 根据 `is_output_agent` 注入完整原题回答职责。Runtime 在执行前根据 `graph.output_agent` 设置该标志；提示词、缓存载荷和输入绑定均使用它。Canvas 的 `output_contract_changed` 因此触发重跑。

所以，只取消重跑而保留这些耦合，会把局部职责下生成的答案冒充完整任务产物；只锁定节点，则限制删除与重建。新设计必须同时改变职责来源、有效性判断和提交入口，不能只改一条 should_execute 条件。

当前图使用低层到高层的有向边和同层双向组件，已经支持 dirty closure。当前代码也已经有连通性循环检测补丁；新方案要迁移并验证这些保护，不能当作完全不存在后重复实现。

## 3. 节点职责：使用明确的交付范围

建议在现有 `set_prompt` 结构中增加一个必填枚举字段（名称暂定）：

```text
result_scope = subtask | task_answer
```

| 范围 | Worker 被要求交付什么 | 能否直接进入最终提交候选 |
|---|---|---|
| subtask | 被委派的局部结果、证据、检查意见或计算步骤 | 否 |
| task_answer | 对完整公开原题的回答，使用本节点职责及可见依赖证据 | 执行成功且当前有效后再检查提交前置条件 |

该字段与原 role/objective/scope/expected_output 一起形成实际职责。task_answer 的系统规则明确要求完整原题回答，局部子职责仅说明完成它的工作范围，不能缩减完整回答义务。

它不是 Worker 输出 JSON 里可自行宣称的“我是最终答案”标签；Runtime 从实际执行配置生成产物来源记录。旧的 subtask 产物不能通过修改元数据升级为 task_answer。

同一 Agent 从 subtask 改成 task_answer 时，调用正常 set_prompt 更新职责，标记其依赖闭包失效并执行。这次重算源于任务范围真实变化。反方向修改同理。

task_answer 只证明“被要求回答完整任务”，不能证明模型事实上答全或答对。模型可能仍返回局部内容或错误答案；不额外引入模型裁判检查答案语义，沿用评分器评价内容与答案格式。空产物、协议失败、严重完整性风险和过期输入仍由 Runtime 阻止提交。

Worker 首次请求、修订请求、工具后的续写和 JSON 协议修复都必须读取相同 result_scope。不能只修第一次提示词。

## 4. 最终选择与提交合并

新文本动作示例：

```json
{"action":"finish","target":"agent_3"}
```

它表示提交 agent_3 在当前可见状态下已经生成的有效 task_answer 产物。

### 4.1 纯评估

先计算 `assess_submission(graph, target, current_candidate)`，检查：

1. target 仍存在且配置完整，职责为 task_answer。
2. 候选属于当前职责、输入、模型配置及依赖版本，未失效。
3. 产物非空、不是协议/后端失败哨兵，严重完整性风险已消除。
4. 图配置合法，保留节点均能沿真实生效关系影响 target；未完成配置和尚未完成的必要计算不能被 finish 隐式跳过。
5. 没有与候选冲突的在途修改或执行；预算和运行状态允许提交。
6. finish 来自真实 Director 调用，而不是控制器补造的成功动作。

### 4.2 一次提交

Director 调用上下文要绑定它看到的图版本及各候选产物引用。target 对应产物在调用后已变化时，拒绝过期请求，不悄悄改为提交新产物。

通过复核后，在同一临界区记录最终 output_agent、图快照、产物引用和 SubmissionReceipt，并终止该题。可保留最终图的 output_agent 字段以兼容报告，但它只记录最终选择，不再决定文本 Worker 的职责或输入签名。

检查失败时，不修改活动图、不设立一个新的“当前输出”、不消耗 Worker token；记录具体 blocker 及合法下一步。拒绝动作仍消耗对应 Director 轮次并计入停滞检测。

同一已提交事件应幂等返回既有凭据；正式提交后禁止继续修改。

### 4.3 没有候选时怎么办

从合法动作菜单移除 finish，同时展示原因：没有 task_answer 职责、产物失效、完整性失败、图不连通或预算不足。允许普通图修改或显式恢复；确实无合法续行时直接记录失败原因并结束。

不由 Runtime 自动挑一个答案、不自动增加汇总节点、不把 summary 或历史局部答案拼成最终回答。

## 5. 增量修改与删除重建

保留现有逐节点配置和修改后执行 dirty closure 的工作方式，不引入全图规划阶段或替换事务。

| 操作 | 预期行为 |
|---|---|
| 修改 prompt/result_scope/模型 | 当前节点及实际依赖闭包失效并重算 |
| 添加尚未连接的节点 | 只执行新增节点及真实受影响部分，已有无关结果继续有效 |
| 新增/删除真实关系 | 按旧、新相关组件和依赖变化失效，不把候选关系当作边 |
| consider_relation 返回 off | 不新增边，不宣称证据已传递或连通性已改善 |
| 修改层级 | 沿用合法性检查及受影响组件的失效规则 |
| 删除 task_answer 节点 | 普通删除；撤销其活动候选，保留历史，受影响存活节点失效 |
| 暂时没有 task_answer 节点 | 可以继续增量执行；不能 finish |
| 创建新 task_answer 节点 | 正常配置、执行、接入证据，当前有效后进入候选评估 |
| finish(target) | 零 Worker 调用，不导致其他候选失效 |

例：A → B → O。删除 O 后保留 A、B，可以创建 N，显式建立 B → N，并让 N 在 task_answer 职责下执行。若 A、B 的输入与职责未变，它们的有效产物可继续使用。

若 O 与其他节点存在双向组件或输出依赖，删除它会影响这些节点，不能保证只执行 N。删除产生的普通中间图允许存在；此时不可提交并不意味着不能继续执行。

节点满额时可先删除再创建，不需要临时占用第九个活动节点。旧节点快照保存在审计存储，不占活动节点名额。

并发执行或恢复时使用节点生命周期和输入版本校验：已删除节点的迟到响应只进历史，不得重新注册节点或成为当前候选。

## 6. 连通性无需绑定某个输出标签才能检查

最终仍保留“所有保留节点能够影响所提交节点”的原有规则，不通过放宽连通性解决失败。

结构评估直接读取真实边，对每个可能的 task_answer 节点计算可达性及 blocker。候选展示可以包含未准备好的节点，但必须与可提交 targets 分开。

针对当前层级有向边 + 同层双向组件结构，可以将双向组件收缩成有向无环图：若有多个终端组件，就不存在一个能接收所有节点贡献的目标；若有唯一终端组件，提交目标须位于该组件，并满足其他产物条件。这是现有可达性规则的计算方式，不是新增必须汇总或必须单节点终点的要求。

因此两个互不连接的节点，不能通过反复 finish 不同 target 变成连通。Director 必须真正连边、合法调整层级或删除不再需要的分支。连接选择为 off 时继续保持未连通，不自动改成 on。

多个 task_answer 节点可以存在，但不代表任意一个都可提交：仍需按真实依赖和最终图规则筛选。

## 7. 统一产物与提交状态

所有状态展示、合法 finish targets、恢复入口和实际提交使用同一个无副作用评估器。

建议返回：

```text
agent_id / result_scope
artifact_id / execution_generation / semantic_input_signature
artifact_current / artifact_integrity
graph_ready_for_target
submit_ready
blockers[]
legal_repairs[] / resource_requirements / remaining_allowance
```

展示“局部结果可用”“完整任务候选有效”“当前图允许提交”三个不同事实，避免用一个 usable 代替所有条件。

非空错误答案或不合数据集答案格式的回答，按实验版现有评分协议处理；result_scope 不是新的正确性判定器。不要把低置信度、不确定性或 verifier 结果当作是否允许提交的依据。

## 8. 缓存、候选和版本

文本执行签名包含任务、节点职责及 result_scope、模型/工具配置、真实消费的上游/同伴产物、执行合约版本等。最终提交 target 不参与 Worker 请求或签名。

需要同时更新当前 cache payload 的 is_output_agent、node_signature 的 is_output、Runtime 开始执行时的角色变化检测，以及 selected-output 的恢复与提示词分支；仅改提示词不足以完成解耦。

保留不可变执行记录，区分最新尝试与当前输入的有效候选。同输入下的一次失败不能直接抹掉仍有效的候选；输入、职责或依赖改变后，旧候选只能留作历史。subtask 的旧产物不能因改为 task_answer 而直接获得提交资格。

候选的完整性证据来自生成它的实际执行和相关依赖；其他尝试的失败保留在全局审计中，不无差别污染有效候选。记录实际请求哈希及语义输入绑定，不能仅凭相同 agent_id 判断可复用。

删除节点不会删除审计记录，但会取消其提交资格。不同节点之间不按答案文本、置信度或金标自动迁移候选。

## 9. 显式恢复与预算

此前的 repair_output 依赖一个固定输出；改为面向具体节点的显式恢复入口，暂名：

```json
{"action":"retry_agent","target":"agent_3"}
```

仅对当前有明确可恢复执行问题的节点开放，不能对健康候选反复重采样。职责升级、新证据接入仍走普通增量修改，不借 retry_agent 修改配置。

- 移除文本 finish 内的隐藏重算、工具恢复和残余 dirty 执行。
- 纯失败重试的题级上限建议初值为 2，属于待验证的新配置；不同节点共享该纯重试上限，不因删除重建而刷新。
- 需要工具恢复时继承失败执行的资源约束，不能仅换 execution ID 获得新 initial 额度。
- 工具额度为零时，已有证据足够的协议重输出可能仍合法；需要新工具结果的恢复则不合法。
- 总 token、总时间、总 Director 轮次以及失败/恢复账本均按题累计，ID、模型路线或 prompt 变化不清零。
- 相同配置的删除重建不能视为新的恢复额度。对任意自然语言改写，不能声称通过哈希就能完全识别语义等价；最终仍由题级硬预算与停滞规则约束。
- 工程/后端请求重试与模型解题恢复分别记账，保留实际调用成本。
- 在配置、执行与恢复准入时保留最终一次真实 Director finish 所需空间，不能依靠控制器补提交。

有限恢复不保证题目能答对；资源耗尽时保留可证实的错误来源与未提交状态。

## 10. 冻结和无进展检测

正常图修改与问题修复都应有可解释的出口。冻结只限制重复无效操作；与当前 blocker 对应且资源允许的修复仍可执行。

没有可提交候选也没有合法修复时，明确终止；不能提供只有必败 finish 的菜单。

进度至少分为：实际图结构/可达性、配置完成度、当前版本有效产物、严重完整性阻塞。重复 finish 不同 target、仅变更 ID、artifact 序号、错误文案或消耗预算都不算问题解决。

合法多步修复（先调整层级再考虑关系）允许经过中间态；使用有限修复窗口及题级预算。已有连通性状态访问记录应保留，不能因为每次出现一个新图版本就无限清零停滞计数。

## 11. 代表性过程

### 单 Agent

ADD_AGENT → SET_PROMPT(result_scope=task_answer) → SET_MODEL → Worker → FINISH(target)。

没有额外输出节点或独立选输出轮次。正确性仍由评分器评价。

### 先探索，后形成答案

允许先创建 subtask 节点收集证据。之后可以修改某个存活节点的职责，使其回答完整原题，也可以新建 task_answer 节点。职责变化或真实新依赖会触发必要执行；已是 task_answer 且输入未变的产物无需在提交时重算。

### 删除原完整回答节点

普通删除，其他节点按依赖关系继续工作。可以暂时没有完整回答节点；后续改职责或新建即可。不存在输出身份交接和自动选择继任者。

### 多个完整答案节点

Director 从当前真正可提交的候选中明确选择 target。选择只在 finish 被接受时生效，不改变其他节点的职责、产物和 Worker 输入。

## 12. 与真实失败轨迹的对应

- 原孤立图连续选输出：新文本协议没有 set_output。重复 finish 不同 target 不能改变真实连通性，也不能清零停滞计数。
- AIME 15：统一完整性状态、显式重试和无路可走时终止，消除“可用却不能提交”及冻结死路；不能承诺工具受限下能够算对。
- AIME 22：若新运行从执行前就将该节点配置为 task_answer，有效答案可以直接 finish，不存在后续选输出触发角色重跑。若它原本被委派 subtask，则仍需职责变更执行，不能为保住历史 754 事后修改标签。
- 原始 286 题的成绩、未提交状态和轨迹保持不变；旧请求响应不能被当成新协议下真实模型生成结果。

## 13. 实施范围与版本隔离

| 模块 | 改动 |
|---|---|
| actions / delegation / Director prompt | set_prompt 交付范围；新文本 finish(target)；retry_agent；移除新文本模式的 set_output |
| graph / contracts | 节点交付范围与候选来源；针对 target 的纯最终验证；输出字段只在提交时定稿 |
| output_contract / runtime | 以 result_scope 驱动 Worker 职责与全部恢复提示；修改签名、失效和迟到结果校验 |
| canvas | 统一候选评估、finish 原子提交、合法恢复菜单与增量删除 |
| adaptive / submission_contract | 去掉隐藏恢复；Director 观察版本绑定；真实 finish 凭据与幂等终止 |
| 回放、训练、PATS、execution_contract | 动作及执行语义版本隔离、候选与角色来源校验 |

以新协议/实验配置启用。旧文本动作、旧输出身份签名和旧缓存保留旧语义，不能无版本迁移。环境任务继续使用原协议分支。正式目录不直接切换。

## 14. 验证与验收

设计阶段已完成一项有限穷举检查：使用现有 Graph 实现，枚举 1–4 个节点的层级配置和每对节点的合法 off/on 关系，共 16,609 种配置；逐节点直接可达性计算与“唯一终端组件”计算所得目标集合一致，未发现反例。脚本与结果保存在 `state/audits/incremental-submission-design-20260926/`。这只核验结构判断，不代表新动作协议、恢复机制或模型效果已经测试通过；本次模型调用为 0。

实施前固定原基线。模拟测试至少覆盖：

1. 单 Agent 完整回答；纯局部阶段无候选；局部升级完整任务必须执行。
2. task_answer 健康产物 finish 零 Worker；finish 失败也零 Worker。
3. 删除唯一完整回答节点、删除重建、节点满额、空图重新建立、迟到响应不能复活旧节点。
4. 新增上游、删除上游、多层结构、双向组件以及无关分支缓存复用。
5. 多终端组件无合法 target；唯一终端组件多个候选；off 不成边。
6. 所有候选健康/全部失效/混合风险；同输入失败保留候选；跨职责和跨依赖版本禁止回退。
7. 非空错误答案按评分处理；空响应、JSON 协议失败、恢复成功的早期工具错误与未恢复严重风险分别处理。
8. 冻结后合法恢复、资源不足终止、剩余 token 但无工具额度、协议重输出不需工具的分支。
9. 重复 finish、变化 target、观察版本过期、重复签发、保存恢复、旧协议混用。
10. 生成 1–4 节点操作序列，检查职责/输入绑定、可达性、预算、终止和提交不变量；生成与业务一致的多步修复以避免过早冻结。
