# SWE 候选提交、协作中断和仓库证据委派：完整改进方案

日期：2026-09-28。状态：**设计方案，尚未实施本文新增机制**。

依据：[最后 30 题中 3 道未提交题的逐题分析](../state/swe-last30-20260928/three-unsubmitted-audit/ANALYSIS.zh-CN.md)、原始轨迹、Worker usage SQLite 账本，以及当前提交、执行、归因代码。

## 1. 目标与已确认事实

本次解决三条路径：

1. 已经形成实际补丁后，仍因图结构、迟改交付职责、收尾动作受限而无法提交。
2. 双向协作在中途被额度或其他故障打断，新的部分结果覆盖或污染旧的完整结果。
3. 委派把题目里的用户复现项目误认成实际可修改仓库，重复寻找不存在的文件。

配套修正用量展示、工具错误恢复和训练归因，使运行行为与报表一致。

| 题目 | 实际 Worker token | 停止时已有的东西 | 直接缺口 |
| --- | ---: | --- | --- |
| sympy-13798 | 360,616 | agent_3 为 task_result，有补丁及修改后的测试证据 | agent_1、agent_2 与最终输出不连通；额度耗尽后不能清理拓扑 |
| sphinx-9367 | 362,193 | 6 个完整产物补丁相同；公开测试共 5 次 41 passed | task_result 设置过晚；最后双向修订没有完整结束，候选 stale |
| django-13112 | 352,461 | 仓库分析和部分执行记录 | 指派修改不存在的复现项目 settings.py，没有完整代码补丁 |

三题共享阈值均为 350,000 个已确认输入加输出 token，所有请求发出时均符合发送条件；最后一次请求完成后超过阈值是现有策略允许的行为。三题没有远程评分，不能据此认定任何一题通过官方测试。

本方案继续使用整题实际 usage 账本；不增加每个 Agent 的 token 配额，不引入预测 token 的准入门槛。历史追加与上下文压缩按用户先前要求另行讨论。Director 的职责、模型选择和图结构仍由策略决定，单 Agent、多 Agent 都应有效。

## 2. 提交资格必须绑定完整证据

保留现有真实 Director FINISH、输入签名、补丁引用、修改后测试和提交事务日志。在这些检查外增加候选生命周期，避免把“保存了补丁”误当成“现在可以提交”。

| 层级 | 含义 | 可以做什么 |
| --- | --- | --- |
| `patch_saved` | 有可信补丁字节、基线和来源 | 后续 Worker 可加载，重新核对并测试 |
| `locally_checked` | 补丁对应明确工作区，存在最后修改后的适用测试记录 | 供 Director 判断；仍需检查职责、图和依赖 |
| `submission_ready` | 同时满足 task_result、输入绑定、完整依赖、最终图和提交协议 | 可由真实 Director 显式 FINISH |

测试记录区分语法检查、公开功能测试、临时回归检查及其真实结果。`locally_checked` 不等于测试全通过；实际测试失败可以带着原始证据提交官方评分。环境没有准备好、测试根本没有执行，不能伪装成有效的功能测试证据。

候选记录至少包含：

```text
candidate_id, question_attempt_id, task_id, base_commit
artifact_id, agent_id, agent_incarnation, original_result_scope
patch_digest, immutable_patch_ref, workspace_snapshot_digest
input_signature, node_signature, execution_contract_digest
consumed_upstream_artifact_ids, consumed_peer_artifact_ids, prior_artifact_id
imported_code_artifact_refs, component_id, component_epoch
latest_edit_event_id, test_event_ids, test_environment_digest
graph_snapshot_ref, readiness, blockers
worker_usage_ledger_id, usage_at_creation, execution_status
```

补丁、测试日志和依赖产物使用不可变引用；摘要用于校验，不能代替原始内容。测试证明绑定具体修改版本：再次编辑后，旧测试不能证明新版本已经测试。

## 3. 提前明确交付职责，显示修改的真实影响

### 3.1 首次执行前指定完整交付职责

当前提示词已经要求完整候选在执行前使用 `task_result`，本次 Sphinx 仍未遵守，因此只重复提示词不够。

在每次 Canvas 观察中增加事实字段：

- `configured_task_result_agents`：哪些 Agent 被委派完整交付。
- `submission_ready_candidates`：哪些候选当前可提交。
- `output_reachability_blockers`：针对候选，哪些保留节点无法影响输出。
- `only_subtask_results`：目前是否只有局部证据。
- `next_mutation_effects`：待选图修改会影响哪些输入、使哪些候选过期，可能触发哪些执行阶段。

允许先探索再建立完整交付节点；不要求第一个 Agent 必须负责最终结果。对于“完整修复并交付”的职责，应在执行前填写 `task_result`。若后来改变职责，必须按新输入执行；不提供零成本重贴标签动作。

### 3.2 修改前保存候选，预览失效范围

对 SET_PROMPT、关系变更、模型变更等操作，使用与实际执行相同的失效计算器生成事实预览：

```text
affected_agents
invalidated_candidate_ids
required_execution_phases
unaffected_candidate_ids
recoverable_submission_checkpoint_ids
```

预览不预测 token。Director 可以看到“这次变更会触发两端初次执行及修订”“当前有可提交候选”，再决定继续改图或提交。实际执行重新校验预览所绑定的图版本，防止预览和执行分歧。

## 4. 保存完整提交检查点，支持有证据的恢复

### 4.1 补丁归档与提交检查点分开保存

现有 `recoverable_swe_candidates()` 主要提供历史补丁；它不能保证当时图、任务职责和输入依赖全部有效。增加独立的 SWE 提交检查点存储。

每当某目标通过完整 `submission_assessment`，保存以下不可变快照：

- 该目标及当时完整、合法的提交图；
- 每个必要产物及其实际消费的上游、同伴和 prior 引用；
- 任务职责、节点 incarnation、执行协议、环境版本；
- 补丁字节、最后编辑版本、对应测试证据；
- 当时的资格检查结果和 usage 账本引用。

运行中的新一轮状态单独保存。后续失败不会改写已完成检查点。记录采用原子写入、内容校验和幂等 ID；进程重启能区分“检查点已完成”和“写了一半”。同一 task attempt 才能恢复，不能跨题、跨基线或跨执行协议引用。

### 4.2 新增显式恢复动作

拟增加 `restore_swe_checkpoint(checkpoint_id)`，由 Director 从当前 Canvas 公布的候选中选择：

1. 校验检查点完整性、原任务/基线/执行协议及所需资源。
2. 构造候选的原始提交视图，在新图版本中恢复该完整状态。
3. 保留后来尝试的全部轨迹与费用，记录 abandoned trial。
4. 进入只允许收尾的阶段；重新观察后，由真实 Director 执行 `finish(target)`。

恢复对象是完整状态，不是把旧 artifact 塞进最新图。新图版本单调增加，原始输入绑定保持原样，不通过重写哈希伪造新鲜度。恢复不能退还 Worker token、工具次数、Director 编辑次数或轮数。

为避免恢复绕过编辑预算，恢复动作只用于不可逆的提交收尾：一旦选择该检查点，就不能再回到 Worker 执行或反复恢复以继续探索。动作及行为变化计入新的执行协议版本。

恢复使用不可变补丁及资源快照；若现有工作区已改变，先验证快照的可恢复性，不能继续引用变化后的路径冒充旧状态。缺失文件、环境版本不符或无法恢复的资源，必须显式阻塞。

### 4.3 不能恢复的情况

- 历史产物当时只有 `subtask` 职责。
- 双向组件未完成其协议要求的同步阶段。
- 依赖产物或测试对应不同修改版本。
- 仅因补丁 SHA 相同，就试图跳过 peer、prompt、scope 或环境变化。

以上只保留为可再加工的补丁证据。仍有额度时，可由 Worker 在新职责下加载并完成工作；已经耗尽时，不制造可提交资格。

## 5. Worker 阈值到达后进入有界收尾

### 5.1 状态和预算

```text
working
  ├─ 正常完成 → finish → submitted
  └─ Worker 达到发送阈值 → closing
       ├─ 当前候选合格 → finish → submitted
       ├─ 可安全清理无关节点 → prepare_swe_finish → finish
       ├─ 存在完整检查点 → restore_swe_checkpoint → finish
       └─ 无合格结果或控制预算耗尽 → 明确终止原因
```

`closing` 禁止新 Worker 请求，包括格式修复、跨路由补发和隐式润色。达到 Worker 阈值不应立即抹掉已完成的模型响应、工具结果或待导出的补丁。

已获得合法响应中的工具动作，按照原有工具次数、超时和路径规则处理；运行时可以完成正在进行的动作、导出与核验现有证据。运行时不能在额度耗尽后自行发明新的测试或编辑动作。已有合法测试完成后可保存结果，无需额外调用模型总结。

建议 `closing_control_budget=2`，支持一次准备/恢复和一次 FINISH；这是 Director 收尾控制次数，不是 Worker token 预留。在有硬 Director 轮数限制的配置中，还必须受剩余轮数限制，不能赠送超限轮数；无轮数限制的 `edits_v1` 配置也由这两个收尾动作限制结束。无效动作照样消耗收尾机会，避免无限循环。

Director 若已发生上下文耗尽或自身接口故障，收尾仍可能失败；该情况记录独立原因。本方案不声称能用候选恢复解决 Director 上下文问题。

### 5.2 安全清理仅阻碍最终图的节点

拟增加 `prepare_swe_finish(target, discard_agents)`，解决 SymPy 这种“候选有效，但保留了不影响输出的组件”的情况。候选名单和可删除节点由 Canvas 通过预检查公布，Director 显式选择。

动作在克隆状态中同时检查：

1. 目标原本就是 `task_result`，补丁、测试及输入绑定有效。
2. 待删除节点不在目标仍然必需的上游或同伴依赖中，删除不改变目标的实际输入、peer 集合、必要产物或资源签名。
3. 删除后不需要任何 Worker 重跑，目标和所需依赖均不新增 dirty 状态。
4. 完整最终图、结构约束、待配置约束和提交资格检查全部通过。
5. 历史导入补丁的原始来源及字节仍在不可变归档里；删除活动节点不删除审计和产物来源。

全部通过才原子生效，进入只允许 FINISH 的状态。此操作只做提交视图的节点裁剪，不新增关系，不改变提示词，不提升 scope，不删除真实依赖以掩盖未完成协作。任何条件不满足，返回具体原因且不部分修改。

本动作作为明确版本化的终结操作，可在 Worker 阈值到达后使用；不增加可供后续探索的编辑额度。普通删节点仍遵守原编辑预算。

SymPy 的最终 agent_3 仅有图不连通阻塞，适合作为该动作的正向验收场景。但仍须回放原输入绑定和补丁导入来源，确认 agent_1、2 的活动状态确实不构成必要依赖；不能只看到“唯一 graph blocker”就直接放行。

### 5.3 Worker 中断时导出部分成果

捕获 `WorkerUsageDispatchStopped` 时，返回结构化 `InterruptedExecution`，至少包含实际执行 ID、停止原因、usage 账本范围、已经完成的工具事件、最后工作区版本、补丁和测试引用。

只有运行时已掌握完整可信资源证据，才可以构造 resource-backed candidate；标明文本汇报未完成，禁止编造 Worker 的解释或判断。原本是 subtask 的仍是 subtask；依赖同步未完成的仍不合格。收尾时再次执行正常资格校验。

若最后只剩“把已保存的补丁与测试写入输出 JSON”未完成，可信资源证据不应随异常丢失。这一步不额外调用模型，不伪造一次成功 Worker 执行。

## 6. 双向协作采用完整轮次发布

当前实现会在修订中途阻塞后保留部分新产物，并把整个组件及其下游标记为未完成。需要保存这些事实，同时确保上一轮完整候选仍有独立身份。

### 6.1 两份状态

- `committed_epoch`：该组件最近一次完整完成的执行状态；其中产物未必具备最终提交资格。
- `trial_epoch`：当前正在进行的初次执行与同伴修订。

二者分别记录角色、节点输入、上游快照、同伴快照、修订策略和各阶段状态。task_result 的完整提交检查点另外通过第 4 节的全图检查产生。

### 6.2 原子发布规则

1. 按真实双向边建立组件与直接同伴集合；不把传递相连节点当作直接可见同伴。
2. 冻结本轮输入，生成 first-pass。
3. 按当前修订协议执行必要 revision；revision 消费的是规定的 first-pass 同伴快照。
4. 所有必需成员与阶段完成，才原子发布本轮组件结果，并按正常规则使下游重新执行或更新。
5. 任一阶段被阻止、失败或未结算，本轮标记 incomplete，保留局部产物与真实费用；不把 first-pass、部分 revision 和上一轮结果混成一个完整组件。
6. 旧完整轮次仍被归档；若整个旧图存在合格提交检查点，可由 Director 显式恢复收尾。

不在资格检查时把 revision 消费的 first-pass ID 偷换成 second-wave ID。各轮的实际信息流必须可重建。

### 6.3 重复工作优化的边界

相同 patch hash 可以提示“补丁未变化”，不能证明 Worker 输入未变化。优先使用已有完整输入签名缓存；缓存键包含任务、职责、角色 scope、实际依赖、模型/执行协议和环境。

纯测试结果只有在基线、完整工作区状态、测试命令、依赖环境、测试工具版本以及可复现条件相同，且测试种类允许缓存时才可复用。随机或依赖动态环境的测试默认重跑。首版可保留现有测试执行，不把宽泛测试去重作为正确性修复前提。

减少 Sphinx 重复消耗的主要措施是初次执行前明确完整交付职责、避免无证据的重复改图、保留完整候选，而不是跳过协议要求的同伴修订。

## 7. 基于实际仓库证据委派

### 7.1 公开事实入口

在工作区准备好后，为 Director/Worker 暴露有界的公开仓库事实：仓库标识、base commit、根目录条目、工具支持的路径/测试格式。引用实际 list/read/search 观察，不注入官方隐藏测试、参考补丁或人工指定的解法。

把三种来源分别标记：

- `issue_example`：题目中的用户项目、示例配置或复现片段。
- `repository_observation`：当前基线/工作区上实际观察到的文件、符号和内容。
- `hypothesis`：尚待调查的路径或修复方向。

题目出现 `DJ_RegLogin/settings.py` 不能自动升级成“仓库里存在这个文件”。

### 7.2 委派增加可验证的目标声明

为路径相关委派增加结构化声明：目标是调查、修改现有路径，还是新建路径；并引用相关观察 ID。

- 调查目标允许尚未确认的路径和符号。
- 修改已存在文件时，绑定该工作区上的存在性证据；证据过期后重新验证。
- 合理的新文件允许创建，但必须确认父目录、写入边界以及其与当前仓库任务的关系。
- 允许同一 Worker 先调查再修复；一旦工具确认可修改路径，更新目标证据，无需强制拆成固定的多角色流水线。

目标未确认时，Worker 仍可调查；运行时不能把未经证实的路径当成必须完成的编辑任务。无法找到委派目标时，返回结构化 `delegation_target_unverified` 及已查过的范围，交由 Director 重定向。

检查依靠结构化路径与真实工具结果，不使用“出现 settings.py 就拒绝”等字符串规则，也不声称仅凭路径检查就能证明修复逻辑正确。

### 7.3 跨 Agent 保留无进展事实

维护整题共享的失败目标表，按基线/工作区版本、规范化路径、目标类型和失败原因索引。

同一证据版本下重复要求编辑已确认不存在的路径，应返回已有失败证据。建议连续两次没有新证据的相同目标失败后，停止该目标的当前执行，并要求新的调查或修订委派；不得用新建 Agent、改写措辞或切路由重置。

仓库状态变化、发现新路径、修正搜索范围或合法新文件目标可以解除该阻塞。正常的独立复核、读取同一个存在的文件，不适用这个缺失目标限制。

Director 观察显示“路径不存在”“本轮无修改”“此前相同目标失败”，由 Director 根据可见框架源码重新委派。对 django-13112，应先确认 Django 框架中相关注册/迁移逻辑的位置；本方案不预置某一段修复代码，也不保证特定函数就是正确修改点。

## 8. 工具能力和测试证据补齐

这些改动服务于三项主修复，并减少已观察到的重复错误：

1. SymPy `bin/test` 的能力描述与参数校验统一：只支持文件/目录时，明确拒绝 `::test_name` 并提供合法目标格式；不让 Worker 通过重试猜接口。
2. 编辑工具的 `ambiguous_edit` 返回匹配数量和有界定位信息，帮助下一次形成唯一匹配；不静默替换多个位置。
3. 测试保护规则在任务能力中声明。需新增回归验证时，可提供受控的临时回归区和执行入口；与只读评分资源分离，临时文件是否进入交付补丁由固定导出策略决定，不能靠 Worker 自述。
4. 对旧依赖兼容性问题，保存同基线、同环境、同命令的 baseline 与 patched 证据。若基线也无法运行，先修公共测试环境，再比较；不要全局忽略所有 warning 或把所有测试失败归为环境问题。
5. SymPy 当前保存的日志有截断，只能确定已看到的几项 DeprecationWarning，不能断言整个测试文件都因同一原因失败。补充完整基线对照是验证任务，不改写历史测试结果。

## 9. 终止归因和训练准入

### 9.1 记录停止原因与结果原因

至少分开记录：

```text
worker_stop_reason
candidate_submission_blockers
submission_status
verifier_status
outcome_status
training_eligible, reward_known, exclusion_reason
```

例如 Sphinx 的停止触发器是 Worker 阈值，而提交阻塞是组件未完成导致 stale；这两者不能合并成“测试不通过”。

### 9.2 使用有来源的错误事件

工具事件保留 `origin`、`code`、操作参数摘要、是否实际执行/产生副作用、受影响资源、恢复事件引用和未解除的阻塞。

`ambiguous_edit`、`invalid_test_target`、`path_not_found`、`protected_path` 根据运行时证据分类，不能只全局扩充字符串白名单：

- 规则已明确、环境正常、参数确定无效的拒绝，可以归入模型动作错误。
- 后续有对应的有效编辑/调用，确认恢复关联后，不再作为未知错误长期阻塞归因；原始错误和消耗保留。
- “需要写回归测试，但系统未提供任何合法路径”的契约冲突，或工具误报路径、挂载缺失，归为运行时问题。
- 服务超时、环境损坏、真实执行结果未知等，没有充分恢复证据时维持未知。

恢复必须绑定具体错误实例及受影响状态，不能只看到同一 Agent 后来某个工具成功，就清除全部历史异常。

### 9.3 评分与排除规则

| 结果 | 评分处理 | 训练处理 |
| --- | --- | --- |
| 官方有效 resolved / unresolved | 使用正式结果 | 按已有有效样本规则纳入 |
| 已证实的本地策略失败，且预算与工具契约执行正确 | typed policy failure；与官方 unresolved 分列 | 按现有策略失败训练规则处理 |
| 未提交且无法可靠归因 | score=null，保留具体阻塞 | 排除有奖励的训练更新 |
| 官方 incomplete_f2p_report / 环境异常 / 结果未知 | score=null | 继续执行用户要求的异常轨迹排除 |

异常样本不得用 0 补齐训练组。准入要贯穿 Solver、Proposer、Frontier、优势归一化和依赖奖励的技能更新；若当前算法要求固定 K 个有效样本，按现有采样规则重新收集或跳过组，不能静默缩小 K。审计日志始终保留。

修复归因不会自动提高官方正确率，也不能把这三题补记为正式 unresolved 或 resolved。历史统计若需要重算，单独生成带新归因版本的报表，保留原结果。

## 10. 实际用量统一从账本读取

当前 `runtime._run_agent()` 捕获 Worker 阈值异常时可能返回空产物和 0/0 token；`evaluation.py` 又从旧执行汇总计算 token_cost，因此部分执行费用丢失。

| 题目 | 原结果表 token_cost | 实际账本 | 少计 |
| --- | ---: | ---: | ---: |
| sympy-13798 | 280,784 | 360,616 | 79,832 |
| sphinx-9367 | 362,193 | 362,193 | 0 |
| django-13112 | 332,463 | 352,461 | 19,998 |

改法：

- SWE 每个 question attempt 的 Worker 使用量以持久账本为唯一结算来源。
- ExecutionReport 记录执行 ID 的已结算增量和 unknown 项；不能依赖是否产生完整 artifact。
- 恢复候选、命中缓存不新计 Worker 用量；之前失败、重试、切路由的请求仍按 request ID 各计一次。
- 导出 `worker_input_tokens`、`worker_output_tokens`、`worker_confirmed_total`、`worker_usage_complete`、`unsettled_attempts` 和账本 digest。
- Director 用量保持独立口径；如总报表需要合计，应明确组成，不能把 Worker ledger 总数再次加到已含 Worker 的总数上。
- 有未结算请求时报告“已确认用量 + 用量未完整”，不填 0，不宣称精确总量。

阈值判断继续沿用现有实际 usage 策略，不因为结果展示修复而新增预算规则。

## 11. 代码改动位置及实施顺序

| 顺序 | 位置 | 改动 |
| --- | --- | --- |
| 1 | `runtime.py`、`worker_usage_ledger.py`、`evaluation.py` | 部分执行结果、真实用量和停止原因完整透传 |
| 2 | 新增 `swe_candidate_store.py`，衔接 `swebench.py` | 不可变候选、测试绑定、完整检查点和重启恢复 |
| 3 | `runtime.py` | 双向组件 trial/committed 分离、完整轮次发布，保留历史输入绑定 |
| 4 | `unified_submission.py`、`canvas.py`、动作解析及协议定义 | closing 状态、显式恢复、受限裁剪、真实 FINISH 事务 |
| 5 | `delegation.py`、`director.py`、`unified_contract.py`、SWE 观察 | 交付职责状态、变更影响预览、仓库证据引用与缺失目标表 |
| 6 | `swe_public_tests.py`、`swebench.py` 及能力描述 | 测试目标格式、编辑拒绝信息、回归验证入口一致性 |
| 7 | `outcome_admission.py`、SWE 归因、`selfplay_runtime.py` | 事件级恢复归因与异常训练排除贯通 |
| 8 | `execution_contract.py`、配置、manifest、测试 | 协议版本和源码指纹完整绑定，固定实验版本 |

前四项是候选和收尾的核心，必须集成验证后一起开启。仓库证据和错误归因可以分开落地，但上线评测时冻结为一个明确的新版本。

新增动作/提交语义需要更新 action、submission、候选和恢复 schema，并同步解析器、Canvas capability、提示词、训练轨迹 reader。新模块和 usage 账本等影响语义的源文件必须纳入 execution contract。不能只改提示词版本或配置开关而遗漏收集/训练的一致性校验。

## 12. 验收标准

### 12.1 离线与组件验证

| 场景 | 必须满足 |
| --- | --- |
| 最后一次合法请求超过阈值，已有合格候选 | 后续 Worker 请求为 0，真实 Director 能 FINISH |
| SymPy 式无关组件阻塞 | 只有输入与依赖完全不变的裁剪可成功；完成真实提交资格校验 |
| 裁剪包含真实上游或同伴 | 原子拒绝，无状态残留，无偷改绑定 |
| 双向修订一端停止 | trial 标 incomplete；不混合发布；旧检查点保留 |
| 旧候选为 subtask | 不能恢复为 task_result，也不能免费提升 |
| patch 相同但职责/同伴/环境变化 | 不用 SHA 相同绕过失效检查 |
| 最后编辑后尚未测试 | 不能依赖旧测试提交 |
| Worker 已执行工具但没有输出最终 JSON | 保留真实资源和费用；仅有充分证据时形成候选 |
| 连续创建 Agent 修改同一缺失目标 | 共享失败证据；新 Agent 不清空该事实 |
| 正常创建新文件或独立读取同文件 | 不被缺失目标守卫误伤 |
| 工具错误已证实恢复 | 不再因该实例永久阻塞归因；未恢复基础设施异常仍排除 |
| partial / retry / failover / cache / restore | 用量与账本逐项一致，无漏计或重复计 |
| 恢复后进程崩溃、FINISH 重试 | 候选与提交日志可恢复；幂等回执不重复创建测评任务 |
| 多轨迹并发 | 检查点、事件和账本以 question attempt 隔离 |

以现有 `tests/test_swe_candidate_integrity.py` 为基础补充状态边界测试；保留现有“图阻塞不能触发无效重跑”“最后合法请求越界仍可提交”等回归覆盖。验证范围围绕上述风险，不扩展无关数据集行为。

### 12.2 三题真实验收

三题从相同基线创建新的 attempt，使用新版本协议、完整新账本和固定运行条件。旧 attempt 已耗尽且协议不同，不能原地增加预算来伪装续跑；历史产物仅用于离线验证，不默认注入新的公平对比运行。

- **sympy-13798**：验证能否形成合格候选并完成回执；裁剪若依赖校验不通过，必须明确解释。公开测试环境的 baseline/patched 差异单独呈现。
- **sphinx-9367**：验证完整交付职责在执行前明确；途中协作失败不覆盖已就绪检查点；不能仅因 41 passed 就代替官方评分。
- **django-13112**：验证不再连续委派修改不存在的用户项目路径，转为基于实际框架证据的工作；最终是否形成正确补丁仍以真实执行与官方评分为准。

验收不承诺三题全部解决。分别统计候选形成率、提交率和官方通过率，区分流程修复与补丁逻辑正确性。

### 12.3 固定最后 30 题验证

三题边界通过后，再对固定的最后 30 题做新版本评测。沿用轨迹并发 15 滚动补位、GPT-student 槽位 10、GPT 非 eco 槽位 5、同池排队/切路由规则、远程测评并发 4。固定题目列表、种子、基线、账本阈值和源码指纹。

报告至少列出：

- 30 题全部的官方通过数、官方未通过数、本地策略失败数、未评分数；
- 有补丁但未提交数、组件中断数、候选恢复数及失败原因；
- 重复同补丁测试次数、缺失目标重复次数、真实 Worker 用量；
- 官方提交数作为分母的通过率，及固定 30 题口径的官方通过比例。

不得删除未知题后只报提高的准确率，也不能用恢复历史候选挑选官方最好分数。每条轨迹由真实 Director 选择最终候选后提交一次；测评传输幂等重试另行审计。

使用现有 Director 服务并保留其占位；需要资源时检查服务器空闲 GPU，不写死 GPU 1。真实远程测评结束后按既有要求确认服务器进入不计费关机状态。本文仅完成设计与本地记录，不启动这些运行。

## 13. 对三题能解决到什么程度

| 题目 | 方案针对的缺口 | 仍需实测的部分 |
| --- | --- | --- |
| sympy-13798 | 有效候选被无关组件阻塞、额度后缺少安全收尾、部分费用漏报 | 裁剪是否保持完整输入依赖；补丁是否通过官方测试 |
| sphinx-9367 | 迟改最终职责、反复执行、同步中断后完整候选丢失 | 原历史 subtask/不完整轮次不能直接补办资格；新版本需重新形成完整候选 |
| django-13112 | 把复现项目路径当修复仓库、跨 Agent 重复错误委派 | 仍需要模型定位并修复真实框架逻辑，当前没有现成补丁可恢复 |

完整落地的标准是：具备可信补丁、职责和依赖证据时能结束提交；证据不足时保留可恢复成果和明确原因；无论是否提交，实际消耗完整计账，未评分异常按规定退出奖励训练。
